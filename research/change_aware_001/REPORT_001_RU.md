# Neural Language — NL-COMP-001 / 001B: результаты инженерного эксперимента

**Дата:** 2026-11-08. **Продукт:** Neural Language `.nir`. **Статус:** подтверждено только на Linux x86-64; **не** доказано новое вычислительное изобретение или преимущество на телефонах.

## Исходное ограничение и решение

После локальных изменений весов сети полный проход выполняет повторную обработку всей структуры. В языке Neural Language уже предусмотрены `weight`, `edge`, `tune auto/incremental/full`. Проверена гипотеза, что существующая модель состояний и эффектов может давать измеримый выигрыш против действительно оптимизированного GEMV (OpenBLAS), а не только против наивного кода.

Исходный C++ runtime взят из старого исходного пакета и сверён с актуальным GitHub `main`: `language/runtime/neural_runtime.hpp` blob `ee71cdab32b248814aa23f26318130bd155c824f`. **В исходном runtime/компиляторе ничего не исправлялось и не переписывалось.**

## Условия и критерии (записаны до тестов)

- Сети FP64 с ReLU и линейным выходом: `128→256→32` и `256→512→128`. Вход фиксирован, меняются веса одного слоя; набор правок за шаг: 1, 8, 32 или 64. Итого 16 сценариев.
- На каждом сценарии 5 испытаний по 250 шагов после 32 шагов прогрева; один и тот же seed и поток правок; порядок режимов циклически меняется; `OpenBLAS/OMP/MKL_NUM_THREADS=1`.
- Измерение включает изменение весов, вычисление результата, обработку соответствующих эффектов и обработку результата; медиана времени на шаг между пятью независимыми испытаниями. В каждой проверке численная траектория сверена с OpenBLAS по всем шагам (предельная нормированная ошибка `≤1e-9`).
- Критерий 20% выигрыша: медианное время `AUTO ≤ 0.8×FULL`, минимум в 4 из 5 парных испытаний. Для отдельной реализации: аналогично относительно полного OpenBLAS.

## Результаты — две реализации одного принципа

| Испытуемый механизм | GCC 14 | Clang 17 | Комментарий |
|---|---:|---:|---|
| Отдельный experimental row-recompute против OpenBLAS | **10/16** | **9/16** | Обнаружены отрицательные случаи при объёмных изменениях |
| Настоящий `Model::AUTO` против `Model::FULL` (оба через тот же OpenBLAS backend) | **16/16** | **15/16** | Важен разный способ накопления дельт и стоимость API |
| Настоящий `Model::AUTO` против отдельного OpenBLAS GEMV | **15/16** | **15/16** | Сравнение менее строгое из-за отличия обвязок/API и двух сборок OpenBLAS |

В отдельном эксперименте **планомерно сохранялись проигрышные сценарии**: простая пересборка изменённых строк не является универсальным улучшением. Настоящий runtime использует накопление изменений эффективных весов, выборочное распространение и полную пересборку после серии обновлений; этот алгоритм существовал в Neural Language до эксперимента.

### Примеры: фактический runtime 0.3

| Сеть / место / правок | GCC FULL / AUTO / BLAS, мкс | Clang FULL / AUTO / BLAS, мкс |
|---|---|---|
| 128→256→32, первый, 1 | 4.09 / 0.42 / 3.38 | 4.16 / 0.44 / 3.37 |
| 128→256→32, первый, 64 | 5.19 / 3.42 / 3.36 | 5.32 / 3.81 / 3.38 |
| 256→512→128, первый, 1 | 22.78 / 1.06 / 22.89 | 23.89 / 1.37 / 22.69 |
| 256→512→128, первый, 64 | 21.59 / 7.49 / 21.09 | 22.20 / 8.69 / 20.84 |
| 256→512→128, последний, 64 | 20.48 / 2.06 / 19.80 | 23.65 / 3.18 / 20.62 |

**Главное отрицательное наблюдение:** на сети `128→256→32` с 64 изменениями первого слоя обычный внешне вызванный OpenBLAS оказался быстрее настоящего AUTO: GCC **3.36 против 3.42 мкс**, Clang **3.38 против 3.81 мкс**. Но сравнение именно `Model::FULL` vs `Model::AUTO` на GCC остаётся положительным за счёт более дорогого общего API полного прохода; на Clang один из 16 сценариев не прошёл критерий повторяемости. Поэтому заявлять «AUTO всегда лучше OpenBLAS» нельзя.

- Численная проверка `runtime_gcc`: 1 082 880 сравнений  максимальная нормированная ошибка 1.2e-15; **PASS ≤1e-9**.
- Численная проверка `runtime_clang`: 1 082 880 сравнений  максимальная нормированная ошибка 1.2e-15; **PASS ≤1e-9**.
- Численная проверка `independent_gcc`: 721 920 сравнений  максимальная нормированная ошибка 2.11e-15; **PASS ≤1e-9**.
- Численная проверка `independent_clang`: 721 920 сравнений  максимальная нормированная ошибка 1.9e-15; **PASS ≤1e-9**.

### Реальные регрессии старого языка

- `tests.test_language` для восстановленной 0.3: **22/22 PASS** (GCC native tests).
- `bash run.sh`: **PASS**, локальная цепочка `.nir → C++17 → native` с обучением, сохранением/загрузкой и независимым предсказанием.
- Полный пакет 0.3 не завершён в текущем запуске: первый попытка с несколькими наборами превысила 120 секунд; считать весь пакет PASS **нельзя**. Архивная карта исходников содержит не все исходные root-файлы 0.3; два отсутствовавших `.nir` отдельно восстановлены из GitHub и сверены по Git blob SHA.
- Sanitizer ASan+UBSan проверил два сценария отдельного экспериментального вычислителя (малые и большие изменения), ошибочных доступов не выявлено. Полный sanitizer audit отсутствует.

## Действительно ли это новая технология?

**Нет, пока нет.** Частичный пересчёт, кэширование активностей, отслеживание зависимостей и выбор стратегия по стоимости известны. Эксперимент подтверждает **условное преимущество конкретного существующего runtime на одном семействе CPU-нагрузок**, но не принципиальное изобретение. Инфраструктура Neural Language пока не обеспечивает полноценного эффекто-зависимого вычислительного IR для произвольного DAG.

Перспектива именно **языка**: выразить в `.nir` разрешённые локальные изменения как типизированные эффекты, компилировать их в явный `ChangeSet` с доказуемой инвалидизацией зависимостей и выбирать алгоритм исходя из формы графа и проверенных затрат; если та же конструкция без потерь реализуется обычной библиотекой, языковая новизна не доказана.

## Ограничения, которые запрещают завышать вывод

- Обе сборки OpenBLAS оптимизированные, но внешняя (`SciPy`, LP64) и используемая в настоящем runtime (`NumPy`, ILP64) — **разные бинарники**. Главная достоверная пара — `runtime_AUTO` и `runtime_FULL` внутри одной сборки/одной API.
- Одна машина `AMD EPYC 9V74`, Linux x86-64; `-O3 -march=native -fno-fast-math`, однопоточный OpenBLAS. Никаких измерений Android, ARM64, NPU, фактической RAM, энергии и нагрева.
- Только последовательные dense-сети FP64, фиксированный вход, правки весов одного слоя; нет обучения в процессе, attention, динамического графа, изменяющегося входа, масок и INT8 в этом сравнении.
- Не сравнивалось с полноценным PyTorch/ExecuTorch/ONNX Runtime Mobile или TFLite/LiteRT на одном телефоне; оптимизированный GEMV — значимый, но узкий конкурент.
- Результаты зависят от веса графа, структуры изменений, компилятора и CPU. Время сборки исходников, latency JNI, память и стоимость хранения кэша в этом опыте не измерялись.

## Принятое инженерное решение

1. **Сохранить текущий эффектовый механизм Neural Language** как подтверждённую для некоторых FP64-нагрузок полезную возможность; не переписывать его ради более медленной отдельной реализации.
2. **Не объявлять новый язык выигравшим на телефоне.** Потребуется физический тест на Samsung A52 или другом указанном владельцем телефоне, с честной baseline и энергопотреблением.
3. Ближайшая языковая исследовательская задача — спецификация `ChangeSet` / правил invalidation при объединении typed IR и DAG с независимым численным эталоном, негативными тестами mixed-layer и input changes. Реализовывать в отдельной ветке после проверки критерия применимости; не объявлять новое математическое открытие.
4. Никаких изменений `main`, существующего компилятора, runtime или скрытых автоматических GitHub Actions. История и исходники сохранены.

Сведения об инструменте и конкретных параметрах сохранены в `metadata.json`; исходные результаты — CSV и JSON без ручной фильтрации отрицательных строк.
