# Neural Language — численный контракт NL-NUMERIC-STRICT-1

Статус: исследовательская ветка fix/canonical-delta-contract-20261110. Не включено в main, не испытано на A52.

## Наблюдаемые результаты

Для валидной программы .nir эталон — Model::forward() с текущими входами и параметрами, тем же FP64 backend и компилятором.

- FULL вычисляет канонический результат либо возвращает канонический кэш, если данные не менялись.
- AUTO и DELTA по умолчанию используют строгий частичный пересчёт строк в том же порядке умножений и сложений, что FULL. Если строгий частичный путь неприменим, используется FULL; команда DELTA не отменяет fallback.
- Если кэш получен приближённым способом, первый строгий вызов выполняет FULL.
- Если веса и вход изменялись до одного predict, промежуточное состояние не исполняется. SGD публикует весовые обновления только после завершения валидации всего шага.
- Наличие BLAS-слоя и правки весов DAG принудительно выбирают FULL, чтобы не смешивать разные порядки суммирования.

Гарантия ограничена: на одном и том же бинарнике, при IEEE FP64 с обычным округлением, без fast-math/reassociation, при использовании публичных операций модели с валидными конечными числами, значения скрытых активаций и прогноза после строгого DELTA/AUTO численно эквивалентны FULL. Знак нуля (+0 / -0) не включён в побитовую гарантию. Разные BLAS-библиотеки и аппаратные устройства не обязаны давать идентичные биты.

Не входит в контракт: прямое изменение публичных Model.layers, input, z, a за спиной runtime после создания кэша; переключение CPU rounding mode; сборки с -ffast-math; NaN/Infinity и значения, отвергаемые finite(); неподдерживаемые операции и топологии.

## Почему прежний алгоритм был небезопасен

Преактивация z, вычисленная и закэшированная с округлением, теряет малые слагаемые при сложении с очень большими. Простое z += W*delta не восстанавливает их. Даже эвристический fallback при почти полном сокращении не обнаруживает все случаи.

Повторно воспроизведённый контрпример: начальный вход [-900000000, 0.00000005, 900000000], первый линейный слой с весами [1,1,1], второй линейный слой с весом 100000000. После observe_delta 1 add 0.1 прежний DELTA выдавал 10000000, а FULL — 10000002.384185791. Ошибка 2.384185791 на выходе превышала допуск 1e-9.

Прошлая алгебра сохранена только при ЯВНОМ native-флаге Model.strict_numeric=false для исследовательских замеров; она не гарантирует NL-NUMERIC-STRICT-1. Обычная .nir-программа не устанавливает такой флаг. Прежние эксперименты ускорения алгебраического DELTA нельзя переносить на новый строгий путь.

## Проверяемое обоснование

1. Начальный валидный cache_canonical получен полным вычислением либо предыдущим строгим частичным вычислением; иначе вызывается FULL.
2. Исходные изменённые координаты входа и изменённые строки весов известны runtime. DAG обходится по топологическому порядку с сохранением порядка конкатенации родителей.
3. Для каждой строки, если ни один вход с ненулевым эффективным весом не изменился и вес строки не был изменён, её численное значение остаётся прежним (за исключением знака нуля). Иначе все произведения строки вычисляются с нуля, в том же порядке, что канонический FULL.
4. Только строки с реально изменившейся активацией становятся источниками изменений для следующих слоёв. Индукцией по слоям все сохранённые значения соответствуют каноническому расчёту. Нет накопления округлений через повторное сложение дельт.
5. Если слои выполняются через BLAS с другим порядком редукции, строгий путь целиком отступает к FULL. После исключения кэш недействителен.

Для штатной команды компилятора принудительно выставляется -ffp-contract=off. Это описание алгоритмического инварианта; универсальное формальное доказательство для произвольного компилятора, libm и устройства отсутствует.

## Приёмка и открытые вопросы

Нужны отрицательные исходные контрпримеры, тесты полного пути .nir, FP64/INT8, линейные сети/DAG, правки весов/масок, обучение и восстановление, длинные последовательности, санкционированные GCC/Clang и sanitizer-запуски.

Стоимость строгого частичного пересчёта НЕ измерена на A52. Частичный анализ зависимостей и повторный проход по строкам могут быть медленнее обычного FULL; старые цифры ускорения на Linux относятся к приближённой алгебре, а не к этой реализации. Нужна отдельная проверка скорости, памяти и мобильного baseline.

До физической проверки и независимого аудита НЕ сливать в main.
